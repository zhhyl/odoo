MFG Custom - Multi-level Approval
=================================

通用多層簽核引擎。為 MFG / PLM Custom 模組群提供可掛載於任意業務模型
（plm_custom.eco、mfg_custom.issue、mfg_custom.quality.check 等）的多層簽核工作流程。

功能
----

* 抽象 mixin：``mfg_custom.approval.mixin`` 為其他模型提供「送出簽核 / 簽核 / 駁回 / 取消簽核」
  按鈕以及 ``approval_state`` 計算欄位。
* 簽核規則：可依「適用單據類型」與「適用條件」過濾，符合條件的單據才走此規則；
  多條規則同時命中時，依 ``sequence`` 由小到大取第一條。
* 簽核關卡：六種 approver 模式
    - ``user``：指定人員（任一核准即可）
    - ``group``：指定群組（任一成員核准即可）
    - ``group_all``：指定群組（全員皆要核可）
    - ``field``：由單據上的 Many2one res.users 欄位決定簽核者
    - ``department``：某部門的在職員工（任一核准即可；不含部門經理本人，
      也只含該部門的**直接**成員，不含子部門）
    - ``department_manager``：某部門的經理
* 金額門檻：可針對單據上的金額欄位設定上下限，只有單據金額落在區間內的關卡才啟用。
* 簽核申請：完整 state machine（draft / pending / approved / rejected / cancelled）。
* 簽核紀錄：保留每關卡的決策者、時間、意見，可於簽核申請單的「簽核紀錄」分頁檢視。
* 通知信：送出簽核時通知**當前關卡**的待簽核者，最終決定時通知申請人。
* 簽核期限：規則可設定「簽核期限（天）」，送出時自動帶出期限日；
  逾期的待簽核申請會由每日 cron（08:00）提醒簽核者，
  簽核申請清單可用「逾期未簽」篩選找出。

可設定的流程（不需改程式碼）
----------------------------

「哪些單據要走哪條流程、幾關、門檻多少」全部由管理員在
**MFG Custom > 設定 > 簽核規則** 設定，**不需要寫任何程式碼**：

1. 新增簽核規則
    * 「適用單據類型」：下拉選擇要簽核的單據類型。**下拉選單只列出已掛載簽核
      功能的單據類型** （測試用模型不在其中）；若透過其他方式選到未掛載簽核
      功能的模型，儲存時會被約束擋下，並提示目前可套用的單據類型。
    * 「適用條件」：用右側的條件建構器（domain widget）挑條件；留空代表全部適用。
      例如「風險等級 = 高」→ 只有高風險的 ECO 需要簽核。
2. 在「簽核關卡」分頁新增關卡，依序由上而下核可：
    * 「簽核者設定」選「指定群組」並挑群組（例：品保部 / 工程部 / 管理部），
      或選「由單據欄位決定」並挑單據上的負責人欄位，
      或選「部門人員」／「部門經理」並挑部門（部門取自 Odoo 內建的【員工】模組）。
    * 「金額門檻」可再限定此關卡只在此金額區間才啟用。
    * 「必經關卡」取消勾選時，若此關卡找不到簽核者會自動略過；維持勾選則送出
      簽核時直接報錯。
3. 儲存後，凡是掛載簽核 mixin 的單據（表單已加入簽核按鈕者）就會出現「送出簽核」
   按鈕；按下後引擎才會依「適用單據類型」+「適用條件」比對出第一條規則並建立
   簽核申請。若沒有符合的規則，會提示該單據尚未設定簽核規則。

關卡是否啟用
------------

* **金額門檻**：設定「金額欄位」與上下限後，只有當單據該欄位的金額落在
  [最小值, 最大值] 區間內，該關卡才啟用；金額不在區間內的關卡不會建立簽核紀錄，
  也不會阻擋整體核准（上限或下限留空視為不限制）。
* **是否找得到簽核者**：
    - 「指定人員」沒有人、「指定群組」沒有有效成員、「部門人員」部門內沒有
      在職員工、「部門經理」部門沒有經理（或經理沒有綁定帳號）、
      或「由單據欄位決定」的欄位為空時，該關卡視為沒有簽核者。
    - 必經關卡（required=True）找不到簽核者 → 送出簽核時直接報錯，
      並提示該檢查什麼（例如「部門 X 的經理 Y 尚未綁定 Odoo 使用者帳號」）。
    - 非必經關卡（required=False）找不到簽核者 → 該關卡略過，不阻擋流程。
* 已停用（離職員工）的帳號不會列入簽核者，避免人員異動卡住流程。

使用者、員工與公司的差別
------------------------

本模組的簽核者一律以 ``res.users`` 記錄。這三個概念在 Odoo 中是不同的東西，
弄混會造成「員工建了卻不能簽核」或「把系統帳號當成簽核者」的問題：

============  ==========================  ==========================================
概念            模型                          意義
公司            ``res.company``             法人／營運單位，決定資料隔離範圍
聯絡人           ``res.partner``             人的聯絡資料（客戶／供應商／員工各一個）
使用者           ``res.users``               系統登入帳號；有權限、能按「核准」按鈕
員工            ``hr.employee``             人事檔案（部門、職位、薪資、考勤）
============  ==========================  ==========================================

``hr.employee.user_id`` 可以是空的 —— **建立員工不會自動取得登入權限**，
這是 Odoo 的刻意設計：不是每個員工都要登入（外包、實習、臨時工、還沒入職），
也不是每個帳號都是員工（系統管理員、客戶 Portal 帳號）。

簽核是「某人按下按鈕」的動作與稽核軌跡，必須綁在能登入、有權限的身分上，
所以：

* **簽核者記 ``res.users``**；
* ``department`` / ``department_manager`` 兩種模式只是用 Odoo 內建的
  ``hr.department`` 推導「哪些帳號合格」，不會另建一套員工資料。

日常維護原則：帳號由 IT／系統管理員建，員工資料由 HR 維護，兩邊靠
``hr.employee.user_id`` 綁定。

哪個帳號參與審批
----------------

**設定 → 使用者裡的那筆帳號（``res.users``）才是參與審批的主體。**
員工（``hr.employee``）不會自己成為簽核者，它只是「推導來源」——
用來算出哪些帳號有資格簽某個關卡。

簽核關卡的簽核者來源：

.. list-table::
   :header-rows: 1
   :widths: 25 60 15

   * - approver_mode
     - 簽核者從哪裡來
     - 簽核者來源是否經過員工檔案
   * - ``user``
     - 直接指定的帳號（``res.users``）
     - ✗
   * - ``group``
     - 指定群組的任一成員（成員就是 ``res.users``）
     - ✗
   * - ``group_all``
     - 指定群組的全體成員
     - ✗
   * - ``field``
     - 單據上那個指向 ``res.users`` 的欄位（例如 ECO 負責人）
     - ✗
   * - ``department``
     - 該部門的在職員工所綁定的帳號（不含部門經理本人、只含直接成員）
     - ✓
   * - ``department_manager``
     - 該部門經理所綁定的帳號
     - ✓

也就是說：**只有後面兩種模式的簽核者「來源」會經過員工檔案**，而且用到的是
「員工檔案 → 對應的帳號」，員工本身不會被寫進審批紀錄。

注意：除了「由單據欄位決定」以外的各種模式，簽核關卡設定畫面上的
「簽核者預覽」都會顯示簽核者的部門與員工狀態（因為那要靠員工檔案才知道），
所以從預覽可以看出被指派的帳號到底是不是在職員工。

實務上最容易踩到的坑：**沒有帳號的員工不能被指派為簽核者，也收不到任何通知。**
因為沒有 ``res.users`` 帳號就沒有權限、也沒有通知管道。
建立帳號有兩條路：

1. 在【員工】建好檔案後，按員工表單上的「送出邀請」→ Odoo 建立帳號並寄設定密碼信
2. 先在【設定 → 使用者】建立帳號，再開啟該帳號表單，按上方的「Create employee」按鈕（需 HR Officer 權限）

【設定 → 使用者】的使用者表單上有「員工狀態」「部門」兩個唯讀欄位，
用來分辨這筆帳號是**真正的在職員工**（在職員工／已離職／所屬部門），
還是**沒有員工檔案的帳號**（非員工帳號，例如系統管理員、測試帳號、客戶 Portal 帳號）——
後者不該被指派成簽核者。

什麼時候需要哪一邊
------------------

============================  ========================================
情境                            做法
新人報到                          【員工】建檔 → 在員工表單按「送出邀請」，Odoo 會建立 ``res.users`` 並寄設定密碼信
IT 先建帳號                       【設定 → 使用者】新增後，開啟該帳號表單按「Create employee」
人員離職                          【員工】封存該員工 → 不再被解析為簽核者；若帳號也要停用，另在【使用者】封存
只有帳號沒有員工檔                     介面會標示「非員工帳號」，代表這是系統／測試／Portal 帳號，不該當簽核者
部門經理沒有帳號                      送出簽核時會明確報錯，請先替經理建立帳號
============================  ========================================

簽核關卡設定時的「簽核者預覽」
------------------------------

在**【MFG Custom > 設定 > 簽核規則】→ 簽核關卡**分頁（把關卡列打開成表單）
下方，會即時顯示依目前設定解析出的簽核者，格式為
「姓名（部門／員工狀態）」，其中員工狀態有「在職員工」「已離職」
「非員工帳號」三種。這是設定時確認人選的依據，避免把系統帳號指派成簽核者。

同一份資訊也放在**【設定 → 使用者 → 使用者表單**（員工狀態、所屬部門兩個唯讀欄位）。

「由單據欄位決定」模式的簽核者取決於單據內容，無法在設定時預覽。

部門模式的兩個注意事項
----------------------

* 「部門人員」**不包含部門經理本人**（避免部門成員互相代簽）。
  若某部門只有經理一人，這個模式會解析不到人、送簽時會卡住，
  錯誤訊息會提示改用「部門經理」模式。
* 部門與員工的維護權限屬於 HR（【員工】模組）；MFG Custom 的管理員只讀取
  部門與員工資料，不需要 HR Officer 權限，也不會被授權修改部門經理——
  否則就能把自己設成簽核關卡的簽核者。

審批入口在哪裡
--------------

* **業務單據表單右上角**：送出簽核 / 核准目前關卡 / 駁回 / 取消簽核。
  「核准目前關卡」「駁回」只在 ``approval_state`` 為 ``pending`` 時出現
  （也就是先由有人「送出簽核」之後）。
* **MFG Custom > 待我簽核**：集中顯示輪到自己處理的簽核申請，
  可從列表直接「開啟單據」檢視內容後核准。
* **MFG Custom > 簽核申請**：全部簽核單，可依狀態、規則、業務模型篩選。
* **MFG Custom > 設定 > 簽核規則**：由管理員設定流程（僅 Manager 可见）。
* 各業務單據的清單頁亦有「審核中／審核已核准」篩選，待辦一眼可見。

簽核者操作
----------

* 單據 form 右上角：「送出簽核」→ 進入待簽核。
* 簽核者登入後到 **MFG Custom > 待我簽核**，可看到待自己處理的簽核申請；
  開啟申請後，可按簽核申請表單右上角按鈕列（button box）的「開啟單據」開啟
  對應的業務單據檢視內容，再按「核准目前關卡」或「駁回」。
* 所有關卡都核准後，單據的簽核狀態才會變成「已核准」；
  任一關卡駁回則整張申請作廢（可修正後重新送出）。
* 「取消簽核」僅適用於草稿／待簽核的簽核單；已被駁回的簽核單請直接重新
  送出簽核以重啟流程。

關卡簽核語意
------------

* 「任一人核准即可」（``user`` / ``group`` 模式）：該關卡第一位核准的人就決定了
  這一關的結果，其他仍待簽的簽核紀錄會被自動標記為「略過」，不再阻塞流程，
  流程直接推進到下一關。（``field`` 模式只會解析出一位簽核者，同理。）
* 「全員皆要核可」（``group_all`` 模式）：群組內每位成員都要各自核准，才算通過。

簽核紀錄與訊息
--------------

* 每個關卡的每位簽核者各有一筆簽核紀錄（``mfg_custom.approval.line``），記錄
  決策者、決策時間與意見，可在簽核申請單的「簽核紀錄」分頁檢視；
  該分頁另可展開「簽核者部門」「簽核者員工狀態」兩欄，確認簽核者的身分。
* 關卡進度訊息（關卡已由誰簽核、駁回意見、所有關卡皆通過）會同時貼在被簽核的
  業務單據與簽核申請單兩邊的 chatter 上。

已掛載簽核功能的單據
--------------------

* ``plm_custom.eco`` 工程變更單（含示範規則：高風險兩關、一般變更一關）
* ``mfg_custom.issue`` 產線問題点
* ``mfg_custom.quality.check`` 品檢單
* ``plm_custom.feasibility`` 可行性評估

本模組另提供一個僅供測試使用的模型 ``mfg_custom.approval.test.model``
（測試用模型），由測試套件用來驗證完整的簽核流程；它已被標記為隱藏，
**不會出現在「適用單據類型」的下拉選項中** （儲存時的約束檢查仍涵蓋它，
測試套件才能對它建立規則）。

掛載新單據
----------

在目標模型的 ``_inherit`` 加入 ``"mfg_custom.approval.mixin"``，
並在該模型自己的 form view 內用 xpath 於 ``<header>`` 插入簽核按鈕即可
（**不要** 用 ``inherit_id`` 指向 mixin 的 view，否則會造成版面錯亂）。

子模型可再覆寫下列 mixin 方法與規則比對條件：

* ``_get_approval_rule_domain()``：回傳額外比對條件，與規則本身的 domain 取 AND
* ``_approval_before_submit()``：送出簽核前的業務檢查（不通過則拒絕送簽）
* ``_approval_on_approved()`` / ``_approval_on_rejected()`` /
  ``_approval_on_cancelled()``：簽核結果回寫到業務單據（例如把狀態改為已核准）

依賴
----

* ``mfg_custom_base`` — 共用群組（User / Manager / Engineering / Quality）
* ``mail`` — chatter、追蹤、mail template
* ``hr`` — 部門與員工檔案（用於 ``department`` / ``department_manager`` 簽核模式）
